## 执行口径

1. 以 AC/BC **原始提交和完整补丁**为责任单位，核对 BC 现有物理合并，再沿定义、声明、调用点、状态、存储与外部契约追踪。提交来源写实际引入者，后续修复只列为关联；本地 commit log 记录原始完整 SHA、物理合并 SHA、所取范围和保留的差异。
2. 相同逻辑或两侧均适用的修复直接共用；`uint16_t`/`U16` 等价类型要连同头文件声明处理。一侧已有的简单诊断打印可以直接保留到两侧，并记录新增日志这一可见变化。仅为了消宏不能覆盖真实产品策略。`AC_ON_BC` 和 `BC_ON_AC` 各自按语义使用；**`BC_ON_AC` 不得与其他定义用 `||` 或 `&&` 组合判断**。确需改变共用业务行为或时序时再考虑 `AC_BC_OPTIMIZE`，相同行为不加优化宏。
3. 同一 `[ALL]` 原因或机制通常在一笔本地提交中闭环。若按用户指定拆分，记录各笔边界及同一原始 SHA，并合起来审查完整原提交；不可只摘容易合并的几行就称原提交完成。没有生产代码变化的已覆盖提交，不计入用户要求的“推进 N 笔生产代码提交”。
4. AC 公开头文件原有注释与声明应整块移到共用宏范围外，保留原文字并核对 AC/BC 可见性；调用方所需头文件同时补齐。没有原始补丁依据时，不改 `goto` 标签、局部 fd 初值、关闭条件、索引或数据搬移公式。PSS `cp()` 的 `0` 初值、`err_exit`、正值 fd 关闭和释放前判空，以及扩容函数的 `img_data_fd = 0`，沿已审定边界保留。
5. 平台、协议、存储布局、产品阈值、事件时序、HUB/云端消息、外部 API 等真实差异保留最小产品分支。跨模块能力未闭环时记原 SHA 和缺失依赖，撤销不完整的 CAP 局部收敛；不从一般代码异味另起未经来源支持的修改。
6. `recog_img_storage.c` 按用户指定区分不影响接口/正常流程的简单收敛与影响实际逻辑的旧文件搬移。判断辅助函数返回值时以其实际布尔契约为准；不能将成功的 `0` 按 `!OK` 错判。复制、扩容、掉电和旧数据兼容的主机用例不能替代设备验证。
7. 已明确的修复应评价完整成功、失败路径和是否新增错误；例如 `bd2d47a7` 去掉入库前重复图片写入是正向修复，但不应据此宣称所有失败结果与旧实现等价。说明结论时区分已验证行为与推断。
8. 标题带 `(1/2)`、`(2/3)`、`(1/4)` 等分段编号的原提交，必须在 CAP、NVMP 等相关仓库追索整组提交和接口依赖，核对各补丁、分支归属及适用范围；未闭环前标记整组，不把单笔局部收敛计作完成。
9. 每次审查、合入、确认已有覆盖、暂缓、撤销或 rebase 后，立即更新 [`merge_status.json`](../branch_diff/face_snapshot/merge_status.json) 中受影响来源的结论、目标 HEAD 和 `last_action`；即使状态不变也记审查结果。批次文档和 commit log 不能代替这一步。
